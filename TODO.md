- [ ] **Convo window: scroll-up pagination is glitchy + has a "dead roof" — two failed fix attempts 2026-07-23, reverted to baseline (unchanged). (Blocks/informs the "map" sidebar feature below.)** Three facets: (a) **jitter** — screen jitters while older messages load on scroll-up; (b) **dead roof** — *some* sessions just won't load more on scroll-up, seemingly random, sometimes cleared by leaving the session and coming back; (c) **UX ask** — when a load fires at the top the viewport gets pushed/scrolled down and you lose your place; ideally it stays put. Root causes found (all in `useChatSessionState.ts` unless noted):
  - **Dead roof** = `handleScroll` only releases `topLoadLockRef` when `scrollTop > 20`, but the scroll-restore holds position by pushing the viewport down by *exactly the height the new page added*. A short page — or one that's all `tool_result` rows (they collapse into their `tool_use`, adding ≈0 visible height) — never pushes `scrollTop` past 20px, so the lock stays `true` forever, parked at the roof with `hasMore` still true. ("Leave and come back fixes it" = the session-change effect resets the lock.)
  - **Jitter** = native browser scroll-anchoring (`overflow-anchor: auto`) *and* the manual restore `useLayoutEffect` both compensate for the prepend → double-correction bounce.
  - Store side is **sound**: `fetchMore` (`useSessionStore.ts`) always makes progress while `hasMore`; the `offset` (counts `tool_result` rows) vs `total` (excludes them) mismatch is **display-only** ("Showing X of Y"), not a loading bug.
  - **Why my two fixes failed:** attempt 2 *removed* the lock so loads gate only on in-flight + near-top — but then every `onWheel`/`onTouchMove` at the top fired a load, and each load's restore nudges down. On real touch (many rapid `touchmove` events per drag) that's a machine-gun of tiny loads all pushing down = "jitters and keeps pushing down, locked in place." **Critical lesson:** the headless Playwright harness (`.scroll-repro.mjs`, discrete 1500px wheel flings every 250ms) does **not** model real touch and gave a false PASS on that regression. **Any future fix must be validated by a hands-on touch test on the actual PWA (build:client → refresh 3001), not the harness.**
  - **Correct-fix shape for next time:** keep baseline's *one-load-per-arrival* intent, but replace the `scrollTop>20` lock-release with something that (i) does **not** depend on `scrollTop` crossing a fixed pixel threshold (that's the dead-roof), and (ii) does **not** re-fire per `touchmove`. Candidates: delta-based re-arm (measure movement away from where the load happened), a short debounce/one-load-per-N-ms gate, or arming on a discrete "reached top" edge rather than a level. Pair with `overflow-anchor: none` on the pane so the single manual restore in the tick-keyed `useLayoutEffect` is authoritative. Symbols: `loadOlderMessages`, `handleScroll`, `topLoadLockRef`, `pendingScrollRestoreRef`, the restore `useLayoutEffect`, the append-anchor effect near `scrollPositionRef`; container in `ChatMessagesPane.tsx` (`onWheel`/`onTouchMove` both = `handleScroll`, so gestures fire even pinned at `scrollTop=0`). Distinct from upstream #1050 (render-side streaming/idle jank) — this is the data/pagination side; complementary. Leftover: `.scroll-repro.mjs` (untracked, repo root) + `/tmp/clide-repro-token` (expires) can be deleted. **M/?**

## Shell sync

- [ ] Shell view shows a stale transcript snapshot and Disconnect/Restart don't reliably refresh it (observed 2026-07-16). Symptom: shell pane showed the conversation as of an earlier point; pressing Disconnect then reconnecting, and pressing Restart, both still showed the old content; it only caught up after something else refreshed. Actual mechanics (code-verified): the Shell tab is a separate `claude --resume <id>` CLI in a server-side PTY — it renders the transcript as of process start and never live-tails turns made in the web chat, so some staleness between restarts is inherent. The two real defects: (1) **Disconnect can never refresh** — client `disconnectFromShell` just closes the WS; the server keeps the PTY in `ptySessionsMap` and on reconnect replays up to 5000 buffered chunks ("[Reconnected to existing session]"), i.e. the same stale view by design (`shell-websocket.service.ts` ~281-308). (2) **Restart resumes a possibly-stale id** — forceRestart kills the PTY and spawns `claude --resume <provider_session_id>`, where the id comes from the sessions DB row for the *UI-selected* session (`server/index.js:128-135`); if the sidebar's selectedSession.id or the DB mapping lags the live session chain (session ids rotate per SDK turn), the fresh CLI resumes an older JSONL fork → still stale. Note: the client-side session handling Haiku suspected is NOT the bug — refs are synced (`useShellRuntime.ts:34-40`) and a disconnect-on-session-change effect exists (`useShellRuntime.ts:103-110`). Fix direction: on forceRestart, resolve the *latest* session id server-side (from the transcript chain / most recent JSONL for that session lineage) instead of trusting the client's possibly-stale id; consider surfacing "resumed at <time>, may be behind" in the shell header. Related side-effect to keep in mind: commands run in the Shell (e.g. `/model`) write into the same session transcript the web chat uses. **M/L** *2026-07-17 follow-up (investigated whether chat↔shell swapping can duplicate sessions — it can't, see notes): (a) correction — "session ids rotate per SDK turn" appears wrong on current versions: all 30 transcripts in the cloudcli project are one-file-per-conversation with stable ids, no forks, so Restart's stale-id risk is lower than written; (b) **defect (3), the reverse direction**: the chat view deliberately ignores `session_upserted` (`useChatRealtimeHandlers.ts:163` — sidebar-only), so turns written from the Shell (e.g. `/model`, or full prompts run in the PTY) never appear in an open chat view until you switch away and back (message refetch happens only on session open). Shell→chat staleness + chat→shell staleness are both display-level; the underlying transcript is a single shared file, so no duplicate sessions arise from tab swapping.*

(1) **The one that bites during dev**: `checkAuthStatus` called `clearSession()` on *any* non-OK `/api/auth/user` — so a reload that lands while the server is restarting gets a 502 from the `tailscale serve` proxy and the token is deleted for good. Now only 401/403 (the server actually rejecting the token) clears it; anything else retries 1s/2s/4s and then keeps the token, so the session survives. (2) A left-open PWA holds a WebSocket and makes no HTTP calls, so it never trips the server's past-half-life `X-Refreshed-Token` logic and the 7d token simply expires → hourly + on-visibility ping of `/api/auth/user` keeps it alive. (3) Refreshed tokens only ever reached `localStorage`; `AuthContext`'s in-memory `token` — which `WebSocketContext` builds reconnect URLs from — stayed pinned at mount → new `persistRefreshedToken()` helper (shared with the file-upload path) fires an `auth-token-refreshed` event the context adopts. Plus a self-heal: token-but-no-user re-checks on visibility/`online` instead of parking on a login form. Client-only, **live after refresh, no restart**. typecheck + lint clean. Upstream candidate (tracked above; overlaps open PR #980). **Not yet live-verified** — the tell is a mid-restart refresh no longer bouncing to the login screen. **S/M**
