## Shell sync

- [ ] Shell view shows a stale transcript snapshot and Disconnect/Restart don't reliably refresh it (observed 2026-07-16). Symptom: shell pane showed the conversation as of an earlier point; pressing Disconnect then reconnecting, and pressing Restart, both still showed the old content; it only caught up after something else refreshed. Actual mechanics (code-verified): the Shell tab is a separate `claude --resume <id>` CLI in a server-side PTY — it renders the transcript as of process start and never live-tails turns made in the web chat, so some staleness between restarts is inherent. The two real defects: (1) **Disconnect can never refresh** — client `disconnectFromShell` just closes the WS; the server keeps the PTY in `ptySessionsMap` and on reconnect replays up to 5000 buffered chunks ("[Reconnected to existing session]"), i.e. the same stale view by design (`shell-websocket.service.ts` ~281-308). (2) **Restart resumes a possibly-stale id** — forceRestart kills the PTY and spawns `claude --resume <provider_session_id>`, where the id comes from the sessions DB row for the *UI-selected* session (`server/index.js:128-135`); if the sidebar's selectedSession.id or the DB mapping lags the live session chain (session ids rotate per SDK turn), the fresh CLI resumes an older JSONL fork → still stale. Note: the client-side session handling Haiku suspected is NOT the bug — refs are synced (`useShellRuntime.ts:34-40`) and a disconnect-on-session-change effect exists (`useShellRuntime.ts:103-110`). Fix direction: on forceRestart, resolve the *latest* session id server-side (from the transcript chain / most recent JSONL for that session lineage) instead of trusting the client's possibly-stale id; consider surfacing "resumed at <time>, may be behind" in the shell header. Related side-effect to keep in mind: commands run in the Shell (e.g. `/model`) write into the same session transcript the web chat uses. **M/L** *2026-07-17 follow-up (investigated whether chat↔shell swapping can duplicate sessions — it can't, see notes): (a) correction — "session ids rotate per SDK turn" appears wrong on current versions: all 30 transcripts in the cloudcli project are one-file-per-conversation with stable ids, no forks, so Restart's stale-id risk is lower than written; (b) **defect (3), the reverse direction**: the chat view deliberately ignores `session_upserted` (`useChatRealtimeHandlers.ts:163` — sidebar-only), so turns written from the Shell (e.g. `/model`, or full prompts run in the PTY) never appear in an open chat view until you switch away and back (message refetch happens only on session open). Shell→chat staleness + chat→shell staleness are both display-level; the underlying transcript is a single shared file, so no duplicate sessions arise from tab swapping.*
