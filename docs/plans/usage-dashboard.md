# Usage dashboard and reset notifications

- Status: 5/6
- Next: Phase 5 — live acceptance at `nuthallpi.tailb083b8.ts.net:3002`.
- Context: [code anchors](../maps/code-anchors.md), [provider capability map](../maps/clide-provider-capability-map.md), [Claude SDK map](../maps/claude-agent-sdk.md), [ADR 0032](../decisions/0032-summary-first-composer-usage-popover.md), and [background-session notifications](background-session-notifications.md).

## Phases

- [x] 1. **Truthful shared usage state.** Keep the existing per-provider usage endpoint and normalized usage shape, but track last successful fetch separately from the latest attempt in both server and client caches. Retain the server's 15-second safety floor, preserve the true successful `fetchedAt` after a failed refresh, and let manual or focus refreshes retry immediately instead of treating a failure as fresh data. Consume Claude SDK `rate_limit_event` messages, merge `message.rate_limit_info` into the cached status, and publish a normalized `provider_usage` WebSocket event without changing the existing composer or settings consumers.
- [x] 2. **Routed account dashboard.** Add Usage to the sidebar Account popover and route it to `/usage` in the main content area, with the sidebar retained and normal browser Back behaviour. Show authenticated providers only, ordered Claude, Cursor, Codex, then OpenCode. Each provider card exposes its core five-hour and overall weekly remaining usage, credit or token balance, and reset countdown plus exact browser-local time; independently collapsed Details hold additional or model-specific windows, reset credits, and account activity. Give the page one Refresh action, preserve the last good values behind a prominent stale warning with retry, and show an honest usage-unavailable state for authenticated API-key or unsupported providers. Localize all new text.
- [x] 3. **Provider reset preferences and delivery.** Extend notification preferences with `events.usageReset: Partial<Record<LLMProvider, boolean>>`, defaulting every provider to off. Add a Usage reset notification toggle to each usage-capable provider's settings page—currently Claude and Codex OAuth only—and omit it for unsupported or API-key usage. When no web-push or desktop channel is enabled, link to Notifications instead of requesting permission or enabling a channel. Deliver through the already enabled system channels using notification kind `usage_reset`, code `usage.reset`, provider/window labels, and `urlPath: '/usage'`; teach notification clicks to honor that path.
- [x] 4. **Reset monitor and durable scheduling.** Run one server-side monitor per enabled provider, refreshing about every five minutes so usage started elsewhere is discovered while CLIde is closed, and schedule exact timers for future provider-issued `resetsAt` values. Cover every displayed limit, including model-specific windows, and coalesce same-provider resets within the same minute. Persist observed and notified reset identities in user-keyed `app_config` JSON so restarts do not duplicate alerts without requiring a database migration. Cancel when disabled, skip resets already past at startup, fire from the provider timestamp even if a Claude access token later expires, and refresh usage after firing.
- [~] 5. **Documentation, checks, and live acceptance.** Add focused client and server coverage for routing, capability-gated settings, freshness, live usage events, scheduling, coalescing, no-catch-up, and restart deduplication. Run typecheck, lint, documentation checks, and client/server builds sequentially. Update the provider and Claude maps plus an ADR for provider-timestamp scheduling and deliberately skipped catch-up alerts. Serve this worktree at `nuthallpi.tailb083b8.ts.net:3002` for personal desktop/mobile acceptance; leave the backlog item in progress until that acceptance, with delivery at a real provider reset recorded separately if no reset occurs during the test window.

- [x] 6. **Review corrections (2026-08-16).** Three defects: `provider_usage` frames carry an empty session id and fall through the chat realtime switch into the open session's realtime buffer, and the kind is missing from `MessageKind`/`GatewayEventKind`; reset timers longer than `setTimeout`'s 24.8-day ceiling fire immediately and record the identity as notified, silencing the real reset (Codex's monthly `individualLimit`); and a live rate-limit push is treated as a complete successful fetch, so it clears `stale`/`error`, advances the success timestamp, and can blank `resetsAt` or the whole credit block for a cache TTL. Three weight items: drop the write-only `observed` identity set; replace the hardcoded `'claude' || 'codex'` in `supportsProviderUsageReset` and `MONITORED_PROVIDERS` with a `usage.reset-alert` flag on the capabilities service, whose contract says provider features belong there and not in React branches; and derive window labels once instead of in three places. Resolved as: the flag is `supportsUsageResetAlerts`, consumed on the client through a new shared `useProviderCapabilities` hook (which also replaces the capabilities fetch embedded in `useChatProviderState`); the two client label sites now share `formatUsageWindowLabel` in `provider-usage/format.ts`. The monitor's own `labelWindow` stays server-side and English, matching every other notification body in `notification-orchestrator.service.js` — translating one body alone would be inconsistent, and is a separate job.

## Done when

- `/usage` opens from the Account popover, preserves the sidebar, and presents every authenticated provider in the agreed order with truthful supported or unavailable states.
- Summary values, collapsed details, local reset times, global refresh, stale warnings, and retries behave consistently across providers without session-level token aggregation.
- Usage reset controls appear only for capable sign-in methods, default off, and use only notification channels the user already enabled.
- Every displayed reset can produce one coalesced notification that opens `/usage`; disabled, missed, and already-notified resets remain silent across server restarts.
- Automated checks pass, the worktree build runs on port 3002, and the desktop/mobile layout receives personal live acceptance.

## Not doing

- Aggregating CLIde session tokens into account usage or inventing estimates where a provider exposes no usage feed.
- Per-window notification controls, threshold alerts, or in-app reset banners.
- A new aggregate usage endpoint, database schema migration, or package dependency.
- Changing existing composer usage-popover semantics or the separate background-session notification plan.
- Committing, pushing, merging, or changing the production service as part of implementation.
