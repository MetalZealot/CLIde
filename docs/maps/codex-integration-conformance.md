# Codex integration conformance

**Status:** Living verification map

**Started:** 2026-08-04 after the upstream v1.37 integration

**Automated entry point:** `npm run test:codex`

This map answers a narrower question than the
[Codex native surface map](codex-cli-sdk-app-server.md): does the Codex behavior
CLIde already claims still survive every application boundary?

The check is deliberately layered. A generated App Server schema can remain
compatible while CLIde drops a renamed option before it reaches the adapter, or
while the live stream works but the rollout parser erases the same item after a
reload. A passing protocol test is therefore necessary but never sufficient.

## Layers and automated evidence

| Layer | Contract being protected | Current automated evidence |
|---|---|---|
| Pinned runtime | SDK and bundled CLI/App Server are the same exact supported version | `codex-app-server-protocol-drift.test.ts` |
| Generated protocol | Required client methods, server requests, notifications, and consumed fields still exist in bindings generated by the bundled binary | `codex-app-server-protocol-drift.test.ts` |
| Browser gateway | Stable app session ID, verified attachment metadata, abort signal, project path, and requested settings reach the provider runtime | `chat-session-addressing.test.ts`, `chat-attachment-filter.test.ts`, `provider-runtime.service.test.ts` |
| Streamed App Server adapter | Initialize, new/resumed turns, transport fallback, Plan reset, model/effort, images/files, approvals, questions, item normalization, usage, abort, rewind, and fork | `codex-app-server-chat.test.ts`, `interactive-request-registry.test.ts`, `image-attachments.test.ts` |
| Run lifecycle | Provider-native IDs can change without replacing CLIde identity; replay and completion remain app-owned and exactly once | `chat-run-registry.test.ts`, `sessions-provider-mapping.test.ts` |
| Persisted history | User/assistant/reasoning/tool/question/usage rows, item IDs, image/file attachments, current and legacy tool wrappers, and fork metadata survive reload | `codex-sessions.test.ts`, `provider-attachment-history.test.ts`, `provider-token-usage.service.test.ts` |
| Browser reconciliation | Pending questions are not duplicated, answers render safely, memory citations stay compact, and optimistic attachment turns reconcile without losing files | `chatHooks.test.ts`, `QuestionAnswerContent.test.tsx`, `chatUtils.test.ts`, `sessionStore.test.tsx` |

Run the suite with the Node installation that owns this checkout's
`node_modules`:

```bash
npm run test:codex
```

The command rejects unsupported Node versions and native-module ABI mismatches
before running tests. On the CLIde Raspberry Pi, that normally means using the
same Node 24 runtime as `cloudcli.service`.

The four numbered groups identify the broken boundary. Do not replace a failed
group with a broad `npm test` pass: the group name is part of the diagnostic.

## What the post-v1.37 regressions taught us

| Regression | Boundary that failed | Guard now in the suite |
|---|---|---|
| Resumed App Server turns used the CLIde ID as the native thread ID | Runtime adapter/native identity | New and resumed turns use deliberately different app/native IDs |
| Abort and pending-request replay used a provider ID after runtimes had switched their process maps to app IDs | Gateway/runtime addressing | Every provider's abort plus reconnect replay is pinned to the app ID |
| One pending request was fanned out across provider runtimes and could be seated twice | Shared interactive registry/browser replay | Provider ownership and request-ID deduplication |
| v1.37 generalized attachments to `files`, but App Server still consumed only `images` | Gateway-to-App-Server option handoff | Mixed image/PDF input is checked at the gateway and App Server turn payload |
| Current Codex rollouts persisted `tools.exec_command` inside an `exec` wrapper, while history recognized only `tools.shell_command` | Rollout parser/history fidelity | Current, legacy, hidden-control, and unknown-wrapper fixtures; unfamiliar wrappers fail visible rather than disappearing |

These are not all App Server protocol changes. Some are CLIde merge-boundary
regressions and one is rollout serialization drift. That is why this suite spans
the application rather than living only beside the generated protocol test.

## Live acceptance matrix

The automated suite starts fake App Server processes and invokes the bundled
binary only for schema generation. It does not create or resume a real Codex
thread, mutate `~/.codex`, or prove installed-PWA rendering. Complete the
smallest applicable live rows after a dependency upgrade, provider refactor, or
upstream integration.

| Live row | What to verify | Required after |
|---|---|---|
| Runtime identity | Diagnostics report the intended SDK, bundled CLI, configured transport, and actual transport | Dependency/runtime or transport changes |
| New then resumed Chat | One sidebar row, one user turn, one final response; the resumed turn stays in the same CLIde session | Any gateway, session-ID, or App Server change |
| Plan then Default | Plan tools appear in Plan; the next Default turn explicitly clears collaboration mode | Mode/capability changes |
| Interactive request | One command/file/permission approval or structured question appears, survives one refresh, and resolves exactly once | App Server, registry, WebSocket, or client replay changes |
| Mixed attachments | One image and one non-image file both reach Codex; reload preserves both attachment indicators | Composer, upload, gateway, adapter, or history changes |
| Tool lifecycle | Command, file change, MCP call, and web search render during the turn and materially match after reload | Normalizer, renderer, or rollout-parser changes |
| Stop | Abort an early first turn and a resumed turn; neither continues in the background or creates a second sidebar row | Abort, run-registry, or session-mapping changes |
| Rewind and fork | Rewind keeps the CLIde session ID; explicit fork creates a new CLIde session with correct lineage | Session/turn identity changes |
| Usage | Context usage updates during Chat and plan/account usage loads without sharing Chat's long-lived process | Usage or App Server client changes |
| SDK escape hatch | With `CLIDE_CODEX_CHAT_TRANSPORT=sdk`, text/image Chat works and App-Server-only capabilities are not advertised | Transport selection or capability changes |

Record accepted live evidence in the
[Codex upgrade ledger](codex-upgrade-ledger.md) for releases, or in
[`docs/todo-done.md`](../todo-done.md) for an integration/refactor. Keep source,
installed dependencies, built artifacts, running service, and live acceptance
as separate states.

## Known blind spots

- Unknown App Server notification methods and completed item types are still
  ignored without a redacted counter. The native map tracks this diagnostics
  gap.
- Synthetic rollout fixtures cover observed shapes, but only a real thread can
  reveal a newly emitted serialization form.
- Installed-PWA lifecycle, reconnect timing, touch behavior, and service-level
  resource use remain live checks.
- The focused command proves the Codex integration contract, not unrelated
  server/client behavior. Run the normal full test, typecheck, lint, and build
  gates when preparing a merge.
